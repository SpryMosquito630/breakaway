# Dedicated Coach section

Coach is a normal fifth tab beside Train, Drills, Analyze and Progress. It opens in **Offline guide · no AI** mode with focus prompts and a message composer. The introductory drill card and "About this coach" section have been removed. This is a fixed-rule catalog matcher, not a language model: equipment, space and saved position constrain recommendations; an explicit supported focus returns only matching skills. Unsupported questions explain the guide's available topics instead of returning unrelated drills. Cards in replies open the existing drill details and practice timer. Saved plan/history/tests are summarized only when asked. No profile/history/plan is changed, and no score is invented. The session-only chat retains the last 20 exchanges and is not saved to disk.

## Private cellular Coach active; production account setup pending

`EXPO_PUBLIC_COACH_REMOTE_ENABLED=true` opts into the Coach connection control independently of `EXPO_PUBLIC_DEVELOPER_FEATURES`. Both flags default off. Enabling Coach does not expose other developer screens. Default/offline Coach never probes the remote service. Unknown age and under-13 profiles cannot connect or send; changing to either aborts an in-flight request and returns to offline mode.

The private paired-phone debug connection is active and verified. Normal production AI still requires account integration. A real exchange requires:

- Either a verified Supabase account session for normal use or the separately paired phone credential for this explicit private debug session. Production account/sign-in UI remains a dependency. The public Supabase URL and publishable key initialize the existing client when the Coach flag is enabled.
- The replay/coaching service configured with server-side `GEMINI_API_KEY` and `GEMINI_MODEL` (preferred for text chat), or `OPENAI_API_KEY` and `OPENAI_MODEL`, plus the existing per-service transport token. Provider secrets never belong in `EXPO_PUBLIC_*` variables. Verified account authentication always takes precedence over private development pairing; request quotas remain enforced.
- A reachable `/api/replay/chat` route (or configured analysis URL). `EXPO_PUBLIC_COACH_REMOTE_ENABLED=true` exposes only protected chat alongside existing player analysis routes; it does not expose the video/food or other developer endpoints.
- Explicit in-screen consent before AI mode. Connecting checks service availability and account authentication or private phone pairing; it sends no chat. The player reviews disclosure and enables AI, then explicitly sends the first question.

The consent and reply labels identify the selected provider (Google Gemini or OpenAI). Each request sends only that message, broad saved position, focus and compatible catalog drill names/cues/IDs. It excludes nickname, age value, body measurements, clips, history, tests and previous chat. Gear and space are applied locally to the allowed catalog. The server's bounded response validator and client validation reject unknown/incompatible drill IDs. Provider output must identify the selected `source: gemini` or `source: openai`; an error never silently becomes an AI-labeled offline answer. AI mode can be switched back to the offline guide at any time outside an active request.

The existing client initialization was reviewed against the current [Supabase React Native Auth quickstart](https://supabase.com/docs/guides/auth/quickstarts/react-native), with no new SDK methods or database/schema operations. Provider secrets remain server-side and the existing server verifies end-user tokens; client getSession is used to retrieve transport credentials, not to authorize the server request.

## Gemini setup and private phone pairing

The server-only Gemini key is configured in an ignored private file. A minimal generic soccer question and an end-to-end Coach question both returned validated live Gemini responses. The adapter uses Google's [generateContent REST API](https://ai.google.dev/api/generate-content), structured JSON output and existing bounded response validation. `gemini-3.8-flash` is a [stable model supporting structured outputs](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash), verified in November 2026. The model remains an explicit server setting rather than an implicit default. Gemini enables text chat only; food/video AI availability remains separately tied to OpenAI.

1. Configure `GEMINI_API_KEY` in ignored `work/replay-service/coach.env.local` (permissions 600), copied from `tools/replay_analysis/coach.env.example`. Keep secrets out of chat and public Expo variables. The loader reads literal values without shell expansion.
2. For normal account-authenticated use, configure the server's Supabase URL/publishable key and the app's corresponding public settings. Existing account authentication is required; this work adds no sign-in UI. Configure `EXPO_PUBLIC_COACH_REMOTE_ENABLED=true` for the Coach UI and protected chat proxy. The existing service bearer token is still required.
3. After coordinating a restart of the existing service, run the same Python environment that runs the analysis service: `python tools/replay_analysis/start-coach.py --env-file work/replay-service/coach.env.local`. The loader starts `server.py` using existing model verification and session-token behavior; restarting changes that token, so restart Metro using `node tools/replay_analysis/start-expo.cjs` with the prior Expo options. Do not start a second server against an active session.

For a controlled local debug test without account infrastructure, the **existing** server `ALLOW_DEV_AI=1` path permits five total attempts per service run. The Coach UI additionally requires `EXPO_PUBLIC_COACH_DEV_ENABLED=true`, a debug build (`__DEV__`) and server-advertised development availability; normal production builds continue to require account authentication. Supabase configuration always takes precedence over development opt-in, including missing/expired JWT rejection. Accountless chat now additionally requires a separately paired phone; the bundled analysis token alone cannot authorize a provider request. Do not expose an unpaired development service on a public tunnel.

`python3 tools/replay_analysis/test_gemini.py` uses mocked transport only to cover structured requests, truthful provider source, missing credentials, auth precedence, refusal/truncation/malformed responses, allowed drills and the fifth-request quota boundary.

### Private cellular debug pairing

For the owner’s private Expo Go test over cellular, enable server `ALLOW_DEV_AI=1` and `COACH_DEV_PAIRING=1`, and the debug app’s `EXPO_PUBLIC_COACH_REMOTE_ENABLED=true` and `EXPO_PUBLIC_COACH_DEV_ENABLED=true`. Keep `EXPO_PUBLIC_DEVELOPER_FEATURES=false`: only health, Joint View, Coach chat and the pairing exchange are routed. Gemini remains server-only; the separate bundled analysis session bearer remains required but is not sufficient to send chat. This is a bounded private development test, not production account authentication.

After the service binds, a one-use eight-digit code is written to ignored `work/replay-service/coach-pairing.json` with permissions 600. Read it locally and enter it in Coach’s masked **Pair phone** field. It expires after ten minutes and locks after five unsuccessful exchanges. The HTTP health response and service logs never include this code. `/pair` accepts at most 512 bytes, requires the current analysis bearer and exchanges the code once for a random 256-bit phone credential. The code file is removed after success. Chat requires that credential in `X-Coach-Pair` before reading a request or reserving quota; it expires after two hours. The client binds stored credentials to the exact service base URL and expiry, uses native SecureStore and memory only on web, and clears them on an authorization failure. A reload on the same native session can retain pairing; a changed tunnel URL requires a fresh pairing code.

The service still allows only five provider attempts per run, including failed provider calls. Pairing attempts and rejected/missing/expired phone credentials consume no provider quota. Supabase configuration takes precedence: pairing is unavailable and an absent or expired account JWT cannot fall back to pairing. Age eligibility and the explicit provider-sharing consent remain required. Production builds cannot use the development pairing UI.

To issue a fresh code or replenish this explicitly bounded development session, the owner restarts the service after coordinating the active Expo session. The ignored `resume-session.py` helper used for the current test preserves the existing analysis bearer, preventing a service restart from invalidating the phone bundle. Never put the Gemini key, phone credential or pairing code into Expo public configuration.

`test_pairing.py` verifies one-use/expiry/guess limits, owner-file permissions, unauthorized HTTP exchange, missing/wrong/expired chat credentials, no quota/provider call before pairing, the fifth-attempt boundary and account-authentication precedence. Proxy tests verify the separate pairing route flag and phone-header forwarding. These tests use no real provider calls.

Public-tunnel browser QA verified the complete private phone flow at a mobile viewport: an adult test profile opened Coach, entered the one-use code, reviewed the Google Gemini sharing consent, explicitly enabled AI, and sent a generic passing question. The service returned a genuine Gemini reply with a compatible **Pass and brake** catalog card. This validates the tunneled UI and provider integration; a physical iPhone over cellular remains the final device check. After QA the analysis service was restarted with the existing bundle bearer preserved, leaving a fresh owner pairing code and five provider attempts; the Expo tunnel stayed running. No pairing code or provider secret is included in this documentation.

Verification for this update: 233 app tests, TypeScript and formatting checks, 20 targeted Python tests (12 coaching, four Gemini and four pairing), and the proxy route tests pass. The downloaded public iOS development bundle was compared with the actual server key; that key was absent. Public health returned pairing-required availability, while chat with only the bundled analysis bearer returned `401 pair_required` before provider use.
