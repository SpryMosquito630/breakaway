# Dormant billing backend preparation

No paid route, store account, database, product, balance, account grant or charging flow is activated. The existing local AI/video service does not import this code. All existing free features keep their behavior. `src/billing/credits.ts` must continue returning unavailable until a real authenticated account ledger exists.

## Prepared boundaries

`tools/replay_analysis/billing_webhook.py` is a framework-independent webhook receiver. `WebhookConfig()` defaults disabled. Configuration is passed only by the future server host, never Expo public variables. Require server-only dashboard Authorization, HMAC signing secret, exact RevenueCat app ID and one environment. Production and sandbox must use separate configuration/storage. The receiver authenticates the original request bytes with constant-time comparisons, rejects bodies over 256 KiB, stale/future signatures beyond 300 seconds, malformed/duplicate JSON keys and mismatched app/environment. Unknown event types are retained without granting anything. Configure the HTTP adapter to accept POST only, limit the incoming body before allocation, pass raw bytes and the two unmodified headers, and return 2xx only after the durable sink commits. Database errors must become retryable 5xx. Never log credentials or raw purchase payloads.

The sink takes the exact `record_billing_event` RPC arguments produced by `receive_event`; it must return the committed SQL boolean. It stores canonical payload/digest by unique RevenueCat event ID. Retries with the same event return duplicate; changed content under the same ID fails. Ingestion is an inbox, not an entitlement verifier, grant, or purchase fulfillment. The sink needs a server credential with RPC access; never send it to the client. HMAC availability must be confirmed in the actual owner's dashboard before this strict receiver is enabled; there is no fallback that accepts unsigned notifications.

`supabase/schemas/billing.sql` is desired declarative schema. Include alongside `connected.sql` in the local Supabase schema configuration, generate/review a migration, run SQL tests/advisors locally, then deploy only as part of an authorized launch. Keep `billing_private` outside Data API exposed schemas. Its event inbox has no client access. Clients can SELECT only their own accounts, operations and ledger entries under RLS. All client mutations and billing RPC execution are revoked. Service RPCs use SECURITY INVOKER with an empty search path; there is no new SECURITY DEFINER bypass. The server role can update balances for settlement and must remain trusted; its credentials are never client-facing. No provided RPC creates accounts or grants credits, and the server role has no account INSERT grant.

The operation ledger implements atomic reservation, success commit and failure release, scoped to account plus UUID operation ID. Account row locks serialize attempts and prevent overspending. Bind a SHA-256 request digest to immutable inputs and derive cost in server code. Reuse of an ID with another cost/digest fails; an identical retry returns existing state without another debit. Release restores the original reserved cost exactly once. Commit and release are terminal; neither can be reversed into the other. There is no seeded production account, bonus, zero display balance or purchase-grant RPC. Account existence does not imply active membership.

## Exact hooks still required before activation

1. Identity lifecycle: link the SDK only to the verified Supabase user UUID after server authentication; define anonymous receipt transfer, restore and logout rules. Provision RevenueCat/Supabase owner accounts and secrets. Never map by client `user_id`, email, creator code or a locally guessed ID.
2. Purchase reconciliation worker: consume the verified event inbox, fetch current RevenueCat subscriber/store state using a server credential, and map the verified purchase to the authenticated owner. Define real product IDs, currency-independent credit quantities, renewal/grant periods, entitlement relationship, expiration and store transaction uniqueness. Implement audited purchase/grant entries and atomic balance crediting in a separately reviewed schema change. No account creation or grant API is provided until those choices exist. Handle duplicate store transactions across different webhook IDs, transfers, out-of-order renewals, refunds, revocations and spent-credit debt before granting. Inbox event IDs alone do not deduplicate a store purchase.
3. Paid analysis host: authenticate every request server-side, enforce current entitlement if the selected product requires it, choose cost server-side, canonicalize inputs, and call `reserve_billing_credit`. Only a newly reserved operation should dispatch work; a returned `reserved` state may already be running. A durable job/result record and unique dispatch claim/outbox must be added before enabling paid work. Persist a completed result and commit its reservation in one transaction; serve that same result on retry. Only release on a verified terminal failure where work cannot still finish. Never automatically release timeout/unknown outcomes or re-run a committed operation. Crash reconciliation and deletion/retention rules remain launch dependencies.
4. Balance endpoint: validate its access token with server Auth, read only that user's actual account, return `{available:true, remaining, verifiedAt}` only when the authoritative account exists; otherwise return unavailable. The local/free analysis endpoints must remain outside this paid flow.

These hooks are intentional activation blockers, not simulated implementations. The existing development-session token in the local replay service is not user authentication and must never authorize billing RPCs.

## Verification

Offline boundary tests: `python3 -m unittest discover -s tools/replay_analysis -p test_billing_webhook.py -v`.

Database test: run `supabase/tests/billing_rls.sql` with `psql -v ON_ERROR_STOP=1` against a disposable local PostgreSQL/Supabase database after applying the desired schema. Fixtures create opening balances only inside a rolled-back test transaction. Tests cover duplicate and conflicting events, exactly-once reserve/release/commit, insufficient funds, request conflicts, terminal-state conflicts, own-only reads and denial of client/anonymous mutation or webhook access. The desired schema and SQL suite passed on disposable PostgreSQL 17.11 with Auth role/UID stubs. A separate two-session concurrency check confirmed that two simultaneous four-credit reservations against a five-credit account produce one debit, one insufficient-funds failure, balance one and one ledger entry. The container was removed. No hosted Supabase or store sandbox transaction has been exercised.
